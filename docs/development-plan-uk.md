# План розвитку chess-tauri-zero

Станом на 26 серпня 2026, після v0.0.2. Синтез усього, що реально
перевірено цієї сесії, і чесний список того, що ще попереду —
без вигаданих термінів, лише пріоритети.

## Де ми зараз (перевірено)

- PyTorch-порт AlphaZero-рушія (2017 → 2026), реальні ваги, MCTS,
  batched GPU inference (~4x на GTX 1050 Ti).
- Повний self-play → train → evaluate цикл, наскрізь перевірений.
- Tauri-додаток: UCI-міст через sidecar, вікно реально відкривається
  й малює дошку (WSLg-скріншоти).
- Панель керування: колір, складність, нова партія/скасувати/здатись,
  спостереження за самогрою, тренування з UI.
- Портативні релізи v0.0.1/v0.0.2: Linux (реально перевірено),
  Windows (крос-компільовано, компілюється чисто, **очікує першої
  реальної перевірки власником прямо зараз**).

## P0 — найближче

1. **Windows-перевірка (в процесі)** — власник клонує й пробує на
   реальній Windows машині прямо зараз. Найважливіший наступний сигнал
   усього проєкту: чи взагалі запускається sidecar (`.venv\Scripts\python.exe`),
   чи коректно рендериться WebView2, чи працює click-to-move.
2. **Hot-reload моделі після тренування** — зараз `train start`
   оновлює `data/model_torch/model_best.pt` на диску, але живий
   sidecar-процес продовжує грати старою моделлю до перезапуску.
   Мінімальний фікс: команда `reload` в UCI-протоколі, що змушує
   sidecar перечитати найкращу модель з диска.

## P1 — коли з'явиться реальний час/потреба

3. **Реальне тренування замість toy-масштабу** — поточний
   `pipeline_torch.py` навмисно малий (2 self-play партії, 1 епоха).
   Щоб модель реально стала сильнішою за `model_best_weight.h5`,
   потрібні тисячі партій і багато циклів — довгий, окремий прогін,
   не одноразова кнопка.
4. **Windows-сайдкар без Python** — `uci-engine-x86_64-pc-windows-gnu.exe`
   зараз лише лаунчер, що шукає `.venv\Scripts\python.exe` поруч;
   якщо власник підтвердить, що це незручно на практиці — розглянути
   PyInstaller-подібне пакування (велике, окрема задача, свідомо
   відкладена в v0.0.1/v0.0.2).

## P2 — стратегічний вибір, не терміновий

5. **ONNX + Rust MCTS замість Python-sidecar** — обговорювали раніше
   цієї сесії: справжній "tauri-типовий" маленький інсталятор (5-20MB
   замість гігабайтів torch+CUDA) можливий лише переписавши MCTS на
   Rust з інференсом через крейт `ort` (ONNX Runtime). Це не рефактор
   поточного коду, а паралельна, велика робота — свідомий вибір
   "легкий реліз vs Python залишається джерелом істини", не зроблений
   ще. Не починати без явного рішення власника.
6. **"Дитина, що вчиться на батьках"** — обговорювали: тренування на
   ВЛАСНИХ партіях власника (не на self-play), записуючи його реальні
   ходи як policy-ціль. Механізм майже готовий (той самий
   `(fen, policy, value)` формат, що self-play вже виробляє) —
   бракує лише запису людських партій у цей формат під час гри.
   Мрія власника на майбутнє, не поточний спринт.

## Свідомо НЕ в плані (перевірено цієї сесії, не помилка)

- Дистиляція від Stockfish чи іншого зовнішнього рушія — порушила б
  "нуль людських знань", принцип, який власник явно обрав зберегти.
- Масштабна ProcessPoolExecutor-інфраструктура оригіналу — окрема,
  набагато важча робота, ніж поточний послідовний, обмежений цикл.
- FTP-розподілена генерація оригіналу — мертвий сервер 2017 року.
